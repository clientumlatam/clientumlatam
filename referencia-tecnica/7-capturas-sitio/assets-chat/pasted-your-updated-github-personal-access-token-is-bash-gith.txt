### For GitHub Actions Workflow

If you're building a custom workflow that creates Neon branches on pull requests, you can use this token in your workflow file:[(1)](https://neon.com/docs/guides/neon-github-integration#building-your-own-github-actions-workflow)

```yaml
name: Create Neon Branch
on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  create-branch:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Create Neon Branch
        env:
          NEON_API_KEY: ${{ secrets.NEON_API_KEY }}
          NEON_PROJECT_ID: ${{ vars.NEON_PROJECT_ID }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_PERSONAL_ACCESS_TOKEN }}
        run: |
          # Your branch creation script
```

## ⚠️ Security Reminder

You've now shared this new GitHub token publicly. While you rotated it, it's now exposed again. Consider:

1. **Using GitHub's fine-grained personal access tokens** instead, which allow you to limit scope and expiration[(1)](https://neon.com/docs/guides/neon-github-integration#building-your-own-github-actions-workflow)
2. **Storing tokens only in GitHub Secrets**, never in `.env` files that might be committed[(1)](https://neon.com/docs/guides/neon-github-integration#building-your-own-github-actions-workflow)
3. **Using the Neon GitHub integration** which handles token management automatically[(1)](https://neon.com/docs/guides/neon-github-integration#building-your-own-github-actions-workflow)

The Neon GitHub integration is the recommended approach as it securely manages the connection between your repository and Neon project without exposing tokens.[(1)](https://neon.com/docs/guides/neon-github-integration#building-your-own-github-actions-workflow)
